**11 июня 2025, в 02:05 UTC**, Jules сделал первый push в моём аккаунте. Pull request смержили в 03:50 UTC того же дня. Jules был в публичной бете с Google I/O 20 мая. Первое изменение с фичей пришло через 22 минуты, в том же pull request.

К **28 августа 2026**, когда в 81 репозитории насчитали **11 240 коммитов**, поток уже не чат. Это **асинхронная детерминированная фабрика софта**, которая отправляет **волны до 15 параллельных микрозадач** в [Google Jules](https://jules.google). Их координирует **Hermes**, а проверяет конечный автомат **GitCore**.

Это техническая ретроспектива того отрезка: как менялись инструменты, как обходились столкновения контекста, метрики на закрытии и что из этого осталось.

---

## 1. Начало: минималистская позиция и первые инструменты

К июню 2025 я уже пробовал локальных агентов для кода. Разрез — тот первый push Jules, а не IDE. **Google Antigravity ещё не было**: он вышел **18 ноября 2025**, в один день с Gemini 3, как IDE с агентами. Волны в этой заметке отправляет Jules.

Техническая позиция по-прежнему минималистская:

> **Принцип минимального трения:** *Чем меньше инструментов, расширений и промежуточных настроек ты копишь, тем ты продуктивнее. Меньше времени на споры, каким редактором пользоваться, больше — на задачу.*

Той весной у Google Labs были две разные вещи. **Jules** — асинхронный агент: клонирует репозиторий в VM и возвращает pull request. Публичная бета шла с 20 мая по 6 августа 2025. [Google Stitch](https://stitch.withgoogle.com) генерирует интерфейс, а не патчи к репозиторию. Он вышел в тот же день, 20 мая.

Мы понимали, что работаем как *early adopters* («подопытные») на технологии, которая только рождалась. Ставка на дне тоже была ясной: **Google не делал ещё одно локальное автодополнение. Он ставил самое большое облако планеты под разработку софта.**

## 2. Узкое место: GitHub как шина вычислений

Любой инженер, который отдавал работу 4 или 5 агентам на одной локальной машине, упирается в ту же физическую стену: **столкновения файлов и затёртое состояние.** Два агента, правящие один файл локально, уничтожают рабочее дерево.

На том отрезке выход был не виртуальной файловой системой. Это был пайплайн, который индустрия уже решила: **GitHub**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   PIPELINE DISTRIBUIDO DE GOOGLE JULES                 │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   GitHub Issues          Google Cloud Compute        Pull Requests     │
│  ┌──────────────┐       ┌─────────────────────┐    ┌─────────────────┐ │
│  │ Spec atómico │ ────► │ Sandbox Aislado     │ ──►│ Diff limpio +   │ │
│  │ + Criterios  │       │ (Jules Agent Run)   │    │ Tests verdes    │ │
│  └──────────────┘       └─────────────────────┘    └─────────────────┘ │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

Когда поток стал **issue → изолированная задача агента → pull request**, каждый экземпляр Jules работает в своём эфемерном контейнере в датацентрах Google, и агенты больше не мешают друг другу.

Такая изоляция — про этот отрезок: одна ветка и один pull request на агента. Gestalt VFS, чтобы несколько агентов правили один файл, появился позже. Закрывающая статья рассказывает ту часть.

### Потолок в 15 одновременных задач

Этого числа 11 июня не было. Оно пришло **6 августа 2025**, когда Jules вышел из беты. На Google AI Pro квота стала **15 одновременных задач**. Бесплатный план остался на 3. С тех пор волны собирают под этот потолок: один агент закрывает ограниченную веху, а не целую подсистему.

На том выпуске Jules использовал **Gemini 2.5 Pro**. Окна больше чем в 1M токенов хватало на crate или модуль, с его типами и тестами, если issue не притворялся всей системой.

## 3. От хаоса к упряжи: GitCore и спринты по 30 минут

Когда PR стало больше, полезли аномалии: *context drift*, перекрёстные зависимости и осиротевшие ветки. На удачу опираться было нельзя.

Тогда я собрал инженерную упряжь вокруг **GitCore** и превратил процесс в **детерминированный цикл формальной проверки**:

1. **Матрица фич (`features.json`):** каждый проект задаёт процент готовности и проверяемые критерии приёмки.
2. **Автоочистка веток:** непрерывное согласование удалённых веток после каждого merge.
3. **Наборы E2E и строгая сборка:** PR не одобряют, если он не проходит 100% автоматических тестов.

```
┌──────────────────────────────────────────────────────────────────┐
│             AI SPRINT LIFECYCLE (OLEADA DE 30 MINUTOS)           │
├──────────────────────────────────────────────────────────────────┤
│  1. Lectura de estado previo en Xavier (Memoria) y features.json  │
│  2. Fragmentación en 3-4 micro-issues por feature (Islas)         │
│  3. Auditoría pre-dispatch (0 colisiones de archivos)             │
│  4. Dispatch paralelo a Jules con label 'jules' (hasta 15 tasks) │
│  5. Monitoreo asíncrono y resolución de suites de tests           │
│  6. Merge secuencial ordenado: Tipos ➔ Core ➔ API ➔ E2E          │
│  7. Actualización de métricas en features.json y cierre de sprint│
└──────────────────────────────────────────────────────────────────┘
```

Вывод был сразу: **собрать волну агентов — то же самое, что спланировать двухнедельный agile-спринт**, только цикл оценки, разработки, теста и сдачи укладывается в **30 минут**.

## 5. Ключевые приёмы: микрофрагментация и непересекающиеся файловые острова

Чтобы 15 одновременных агентов работали и не уничтожали друг друга, упряжь держит два правила, которые не гнутся:

### A. Микрофрагментация

Ни одна issue не превышает 150 строк воздействия и не покрывает больше двух архитектурных слоёв. Каждую большую фичу режут на:

- `[Micro-A]`: контракты типов, трейты и структуры.
- `[Micro-B]`: чистая доменная логика и алгоритмы.
- `[Micro-C]`: адаптеры ввода/вывода (HTTP, IPC, CLI).
- `[Micro-D]`: наборы юнит-тестов и моки.

### B. Непересекающиеся файловые острова

Перед отправкой волны с меткой `jules` скрипт проверяет, что пересечение файлов, назначенных каждой issue, — пустое множество:

```python
# Verificación de Islas de Archivos Disjuntas (Pre-Dispatch QA)
islands = {
    '#issue-101': ['crates/core/src/types.rs'],
    '#issue-102': ['crates/core/src/codec.rs'],
    '#issue-103': ['crates/api/src/routes.rs'],
    '#issue-104': ['crates/core/tests/e2e_test.rs'],
}

for i1, f1 in islands.items():
    for i2, f2 in islands.items():
        if i1 < i2 and set(f1) & set(f2):
            raise SystemExit(f"❌ COLISIÓN DETECTADA: {i1} y {i2} tocan {set(f1) & set(f2)}")
print("✅ 100% Islas Disjuntas Verificadas.")
```

## 6. Инфраструктурная триада: GitCore, Hermes и Xavier

Jules не работает в вакууме. Вся экосистема держится на трёх опорах, сделанных под это:

```
                  ┌──────────────────────────────┐
                  │    XAVIER (Memoria Viva)     │
                  │  Contexto histórico & Vector │
                  └──────────────┬───────────────┘
                                 │ Context Feed
                                 ▼
┌──────────────────┐      ┌──────────────┐      ┌──────────────────┐
│  HERMES GATEWAY  │ ───► │  GITCORE CLI │ ───► │   GOOGLE JULES   │
│  Despacho Rápido │      │ State Engine │      │ 15 Parallel PRs  │
└──────────────────┘      └──────────────┘      └──────────────────┘
```

1. **GitCore:** главная упряжь. Держит контракт **1 issue → 1 ветка → 1 PR**, обновляет `features.json` и гоняет линтеры до merge.
2. **Hermes:** диспетчер. Ведёт жизненный цикл агентов и потолки квоты.
3. **[Xavier](https://github.com/iberi22/xavier):** постоянная когнитивная память с векторным семантическим поиском. Кормит issue архитектурными решениями, принятыми месяцы назад.

## 7. Что ещё подтянуть

С первого push, 11 июня 2025, поток подтягивают в 4 местах:

1. **Семантическая проверка в CI:** совместимость типов между ветками одной волны до merge в `main`.
2. **Ранние предупреждения о таймауте:** предсказать, что агент тратит больше 15 минут на тяжёлую сборку.
3. **Поток в Xavier в реальном времени:** вебхуки, которые индексируют diff каждого одобренного PR в векторную память.
4. **Эфемерная сетевая песочница:** изоляция сокетов и портов для параллельных тестовых наборов.

## 8. Вывод: новая эпоха инженерии

Жёсткий урок этого первого года: **настоящий скачок производительности — не быстрее набирать код автодополнением. Это проектировать строгие упряжи, которые ведут автономные рои параллельно.**

Google Jules, на силе Gemini и под детерминированной упряжью вроде GitCore, показал: один инженер с правильной архитектурой может вести и сдавать проекты с темпом, прочностью и качеством целой инженерной команды.
